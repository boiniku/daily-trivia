# 重大不具合の修正・検証（2026-09-14）

## 結論と適用範囲

前回のレビューで挙げた重大7項目を対象に、ローカルコードの修正と回帰テストを追加した。
本番DB・配信中の1.1.0・App Store Connectには変更していない。
この作業によって配信中ユーザーの失われた表示が復旧した、と判断してはならない。
実機試験とPostgreSQL同時実行試験は未実施であり、現時点では公開承認ではない。

| 問題 | 実装した対策 | ローカル検証 |
| --- | --- | --- |
| 管理用削除APIが無認証 | Firebaseの署名・失効確認とadmin=trueのカスタムクレームを必須化。daysは1〜36500に制限 | 未認証・一般ユーザー・負数等ではDBを開かないHTTPテスト |
| 任意UIDによる履歴移管 | 旧/auth/mergeは410で拒否し元データを保持。検証済み経路はApple連携先を確認し一度移管したソースの他アカウントへの再移管を拒否 | 未検証経路拒否、別アカウントへの再利用拒否 |
| 端末履歴の同時移行 | 読み出し時の移行も排他制御。所有者を先に予約し、書込失敗時は同じ所有者だけが再開。元キーを回復用に保持 | 同時読取、保存失敗、破損JSONの非上書き |
| Apple連携失敗後に再試行不能 | 匿名認証中に選択したApple subjectをサーバーへ保存。連携後はFirebase Adminで取得したApple subjectと照合。起動・復帰・前景中の定期処理で再試行 | 旧トークンなしの再試行、別Apple subjectの拒否、応答喪失後の再実行 |
| 通信待ちがローカル保存を停止 | 通信は保存ロックの外へ移動。返却データは最新ローカル状態に追加マージ。HTTP本文読取まで15秒で制限。キャッシュがあれば地図を先に表示 | 未完了通信中の新規保存、応答による保存済みデータの非消失、タイムアウトとAbort |
| 削除後の同期でデータ復活／Firebase未削除 | 削除待ちを端末に永続化。通信を停止してから削除。サーバーに削除状態を残し、PostgreSQLトリガーと同じアカウント単位のロックで遅延書込を拒否。Firebaseユーザー削除とApple認証取り消しを実装 | 遅延応答、Firebase削除失敗後の再試行、削除済み状態での送信拒否、別Appleアカウントの取り消し拒否 |
| 復元されたログイン状態が課金SDKと未連携 | Firebase起動時の認証通知からRevenueCatのconfigure→logInを直列実行。古いアカウントの結果を破棄し、購入中のSDKアカウント変更を待機 | 起動順序、アカウント切替、連携失敗と再試行、購入中の切替 |

通常履歴・お気に入りの移管についても、実運用と同じautoflush=FalseでCollectionItemが残ることを検証した。
永続IDの対応が存在する場合、後から同じ本文の別地点が追加されても解放記録をそちらへ付け替えないよう修正した。

## 公開前に残る確認

1. 使い捨てPostgreSQLで`test_account_lifecycle_postgres.py`を実行。`TEST_ACCOUNT_DATABASE_URL`はlocalhostの`daily_trivia_test_*`というDB名だけ許可する。削除と書込の両方向の競合、移行DDLの再実行を確認する。
2. ステージングでアプリ用DBロールの権限・RLSと新トリガーの組合せを検証。起動時の`migrate_account_lifecycle`が必須。本番データのバックアップと復元手順も確認する。
3. iPhoneで、匿名／Appleそれぞれの1.1.0からの上書きアップデート。解放ID・件数・日時・通常履歴・お気に入りを前後比較する。アップデート試験ではアンインストールしない。
4. Apple連携の各段階で通信遮断・強制終了を行い、同じAppleアカウントで再開できることを確認する。過去のバージョンで既に失われた匿名認証情報は、この新方式だけでは後から証明できない。
5. Apple登録済みユーザーの再インストール試験は、サーバーへのバックアップ完了を確認したテスト端末でのみ実施する。匿名ユーザーのアンインストール後復元は保証しない。
6. Appleの再認証・取り消し・Firebase削除を実機のテストアカウントで確認。通信切断後に削除が保留になった場合、成功と表示せず再試行が必要。削除済みFirebaseトークンでの再試行は署名と有効期限が検証できる間に限る。
7. RevenueCat Sandboxで購入済み起動・購入復元・未購入アカウントへの切替を確認。ダッシュボードの購入移管設定は本作業で変更していない。

## 互換性とリリース順序

- 旧UIDだけの移管APIは安全性のため停止する。1.1.0からの新規アカウント移管はエラーになり得るが、ソースの履歴は削除しない。通常の地図・履歴取得APIの形式は維持した。
- 新アプリのApple移管には`durable_apple_merge_v1`、削除保護には`account_deletion_barrier_v1`対応のバックエンドが必要。
- 先にステージングでDB移行を検証し、その後バックエンドを反映してから新アプリを配布する。本作業ではいずれもデプロイしていない。
- `verify:production-backend`に必要なcapabilityを追加した。ただしこのスクリプトはビルドへ自動接続されていないため、単独の必須リリース確認として扱う。
- cleanup APIの運用者にはFirebaseのadminカスタムクレームが必要。期限付きの無認証移管用環境変数は削除した。

## 購入復元の追加修正・再検証

前回の30件だけでは、同じアカウントの前景復帰と復元処理の競合を検出できていなかった。以下を追加修正した。

- 同一UIDの再通知・前景復帰では、アカウント切替の世代番号を変更せず、確認済みの購入情報を消さない。連携済みならgetCustomerInfoで再確認する。
- 同一UIDの再確認が通信エラーになっても、同じ実行セッション内で確認済みの有料状態を維持する。別UIDへの切替時は状態を消し、権限の混入を防ぐ。
- 取得に成功し有効な権限がなくなった場合は、その結果を反映する。期限切れを常に有料扱いにする変更ではない。
- 復元結果に有効なpro権限がある場合のみ「復元完了」を表示する。該当なしの場合は別メッセージを表示し、購入済みユーザーには再購入を促さない。
- 再確認の失敗が、その後の復元・購入の処理キューを止めないようにした。初回のアカウント連携失敗時は、購入処理を開始しない。

モバイル自動テストは42件成功（追加12件）、型チェック成功。実際のRevenueCatProviderのイベント処理・有料状態更新・通知メッセージもモックで確認した。ネイティブSDKやAppleとの実通信、実機の画面操作を実施したという意味ではない。
コールドスタート時のオフライン復元、RevenueCatの移管設定、購入済みSandboxアカウントでの再インストール・実機復元の確認は引き続き必要。本番設定変更・課金操作・ビルド・デプロイはしていない。

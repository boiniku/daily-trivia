# お気に入り等の保存状況とデプロイ調整

## 追加対応: 1.1.0からの地図記録の保持

- 旧ローカルキーを残したままユーザー別の保存先へコピーする既存処理を、匿名UID／Apple UIDそれぞれでオフライン更新のテストに追加。通信失敗でも元のJSONと解放記録を保持する。
- 地図一覧の再取得が空／一部だけでも、キャッシュにある過去の掲載情報を削除しないよう変更。サーバー一覧から欠けた項目は配信終了扱いで保持し、解放状態は現在のユーザーの記録から付与する。配信終了項目は地図ピンではなく解放済みコレクションに残る。すでにキャッシュから消えた本文をこの修正だけで復元することはできない。
- HTTP 200だけをバックアップ完了と扱わないよう変更。サーバーの解放記録と旧IDの対応を照合し、未承認IDや通信中の未送信追加があれば同期結果をfalseにする。元の記録は削除せず次回同期へ残す。古いサーバーが復元用の記録を返さない場合も成功にしない。
- Apple UIDで旧記録をアップロード→端末ストレージ全消去→別Apple UIDでは空→元Apple UIDで復元、という往復テストを追加。これはモックの保存先によるロジック検証であり、App Store更新・実機再インストール・本番Firebase認証を検証したものではない。
- 再実行結果: モバイル50件成功、型検査・リリース設定検査成功。API164件中162件成功、PostgreSQL同時実行2件スキップ。ビルド番号151を維持。ビルド、アップロード、push、デプロイは実施していない。

保証の境界: 通常更新で端末記録を初期化しないことと、再インストール時の復元は別。後者には対応バックエンドへの保存完了と同じAppleアカウントでの認証が必要。未送信のローカル記録はアンインストール後に復元できない。既存の所属不明484件と旧移管APIの互換性問題は下記のとおり未解決であり、現時点を公開可能・復旧完了とは扱わない。

## 今回確認できたこと

- 本番 `/health` は `environment=production`、コミット `e5b94d22228f6cc3c804723852216f7378194c87` を返した。今回のローカル変更は未反映。
- `apps/api/.env`から解決される接続先DBに、READ ONLYトランザクション・5秒のSQL制限で集計のみ実施。Render管理画面の実際の接続URLとの照合は未実施。
- コレクション2,552件、保存明細76,687件。そのうち484件で`collection_id`がNULL。非NULLのIDから存在しないフォルダを参照する明細は0件。
- 同一ユーザー・同名フォルダの重複が182組存在。
- 484件はお気に入り・閲覧履歴・カスタムフォルダのどれだったか、現在の明細だけでは特定できない。CollectionItemにはユーザーIDが直接保存されていない。
- 対象行の保存日時は2026-02-15〜2026-09-03。これは「保存した日時」であり、紐づけが壊れた日時ではない。1.1.0からのアップデートが原因と断定できない。
- publicスキーマには、今回の名前検索で該当するバックアップ・監査テーブルを見つけられなかった。Neon側のバックアップ／復元履歴の有無は別途確認が必要。

## 再現した不具合と修正

`GET /collections`は同名フォルダを自動統合する。移動先のcollection_idを設定した後、その更新がDBに反映される前に古いフォルダを削除していた。実運用と同じautoflush=Falseでは、SQLAlchemyの関連処理が明細のcollection_idをNULLにする。

テスト用の「Appleユーザーのお気に入り1件」を取得したところ、修正前は明細が残ったままフォルダIDがNULLになり、画面向けの件数は0になった。このコードは現在の本番コミットにも存在する。ただし、実DBの484件すべてがこの経路によるものと確定したわけではない。

ローカルでは移動のflushをフォルダ削除の前に追加した。既存484件を復元する変更ではなく、再発防止の変更。DBの集計以外の操作、本番デプロイ、GitHubへのpushは実施していない。

追加した4件のテスト:

- 同じ匿名UID／Apple UIDで繰り返し一覧を取得しても、保存した雑学と日時が残る。
- お気に入り・閲覧履歴・カスタムフォルダの重複統合で、一意な保存明細と日時が残る。
- 匿名からAppleへの移管で双方の保存内容を保持し、別ユーザーへ影響しない。再実行も可能。
- DBエラーが発生した移管では、双方の元データへロールバックする。

API全体は164件中162件成功、PostgreSQL同時実行2件は未設定でスキップ。実機アップデート・RLSをこのSQLiteテストで検証したという意味ではない。

## デプロイ順序案（まだ実行しない）

1. 現在のDBバックアップと、紐づけが残っている過去の復元時点を確認する。Renderの実管理設定で自動デプロイOFF・接続DBを照合する。リポジトリのautoDeploy=falseだけでは、実設定の保証にはならない。
2. 現在の本番コミットを基点に、一覧取得の再発防止だけを独立した修正として準備・テストする。今回の認証変更・旧移管API停止・新DBトリガーをまとめて先行デプロイしない。この修正は1.1.0が使うAPIの入出力を変えない。
3. 対象コミットを確定してから再発防止修正を本番へ反映し、正常な保存件数・紐づけなし件数・エラーを確認する。現時点ではこのデプロイを実施していない。
4. 過去のバックアップを分離環境へ復元し、明細ID・雑学ID・保存日時などから元フォルダと元ユーザーを照合する。所有者を確定できた行だけを復旧対象にする。稼働中DB全体を過去へ戻すと新しい記録が消えるため、全体巻き戻しを復旧手順としない。
5. 新アプリ用の移管・削除保護は、ステージングPostgreSQLと1.1.0／1.1.1の実機で別途検証する。その後、互換性を確認したバックエンド→アプリ配布の順で進める。

## 新版公開前に未解決の互換性

1.1.0はAppleログイン後に旧`/auth/merge`を呼び、失敗してもAppleユーザーへ切り替わる。旧経路を410で止めると、匿名時代のサーバーデータを表示できなくなる場合がある。元行が残ることとユーザーがアクセスできることは別で、後日のアップデートだけで必ず復旧できるとは言えない。

一方、旧経路は生のUIDだけで移管元を指定し、所有権の証明がない。この経路をそのまま維持することにも権限上の問題がある。新バージョンを先に公開するだけで、残っている1.1.0の問題が解決するわけではない。安全な移管証明の扱いと旧版ユーザーの更新・サポート方針を決めるまで、現在の変更一式を本番へ出さない。

今回の確認環境にはRender APIのキー・サービスIDがなく、実管理設定は未確認。以前の「pushだけなら影響なし」という説明はリポジトリの定義を根拠にしたものであり、実環境を確認した保証ではない。

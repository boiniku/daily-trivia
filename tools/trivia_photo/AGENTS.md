# 毎日雑学 Photo Codex Harness

このフォルダで「写真を集めて」「次の5件」「続きから」と依頼されたら、
**[docs/harness/collect.md](docs/harness/collect.md)を読んで、確認用R2への保存と検証まで進める。**
途中の判断はこのセッションのCodex自身が行う。別のAI API・SDK・モデルへの委託を追加しない。
PythonはDB取得、写真検索・取得、画像加工、判断JSONの検証、R2保存、状態管理を担当する。
`collect`単体は対象の取得まで。Codexが`search`→画像を実際に見る→`select`を実行して収集を完了する。
`trivia_usagi`のAGENTS→工程別手順→Pythonツール→実物を確認→記録という方式を採用する。

| 依頼 | 工程に入る前に読む手順書 |
| --- | --- |
| 写真収集・再開・選び直し | [docs/harness/collect.md](docs/harness/collect.md) |
| 写真と権利の選定 | [docs/harness/select.md](docs/harness/select.md) |
| 確認画面・検証 | [docs/harness/review.md](docs/harness/review.md) |
| 確認済み画像をアプリへ反映 | [docs/harness/publish.md](docs/harness/publish.md) |

「選び直し待ちを進めて」の依頼では`review-queue`でR2の依頼を読み、理由を反映して元のバッチで`search --refresh`する。保留は勝手に再収集しない。

手順をユーザーの依頼文へ書き写さない。新しいセッションもこの入口から再開できるよう、
実行方法と判断基準はこのフォルダへ残す。開始時に`list --batch latest`で既存の状態を確認し、
続きの依頼なら保存済みのバッチを使う。新規の依頼なら新しいバッチを作る。

# このプロジェクトの作業境界

- 実装・設定・手順書は`trivia_photo`に置く。画像と作業履歴の正本はR2。ローカルの作業JSON・HTMLは再生成可能なものだけにする。
- `../毎日雑学`は原則読み取りのみ。ユーザーの依頼により、既存の管理画面への写真確認の追加とその接続部分だけ変更してよい。
- モバイル・本文・既存の収集機能は変更しない。クレジット表示はユーザーが後で実装する。
- 本文は確認済みとして扱う。真偽確認・裏取り・本文修正を追加しない。
- 実行は手動。定期実行・スケジュール・バックグラウンド収集を追加しない。
- 収集時は1雑学につきおすすめ1枚と別候補を用意する。管理画面ではユーザーが候補から複数枚を採用できる。採用順の先頭を表紙とし、各写真の出典・権利情報を保持する。一般的な主題には一般的な写真を許容する。
- 固有の対象・出来事はそのものの写真を優先し、意味のある参考写真を許容する。
- 動物の内部構造などの一般的な雑学に、解剖写真を必須にしない。
- 画像は既存アプリの16:9・cover表示に合わせる。Codexは`inspect`でR2の画像をメモリから表示し、全体版も比較して選ぶ。メタデータやファイル名だけで選ばない。
- 候補・全体版・採用画像をローカルへ保存しない。画像の加工・検証・表示はメモリ上で行う。スクリーンショットや画像キャッシュもこのフォルダへ残さない。
- 画像のライセンス・作者・出典・加工内容と、写真に写った対象の追加の利用条件を確認・記録する。
- 接続情報を表示・コミットしない。既存の設定ファイルは読み取るだけで変更しない。

# 収集と反映

- `collect`はNeonをSELECTして対象と状態をR2へ保存する。`search`は候補を確認用R2へ保存し、`select`はその候補から1枚を選んだ記録をR2へ保存する。
- CLIの`approve`は判断結果をR2へ保存するだけ。既存管理画面はユーザーの2026-10-16の指示により、採用ボタンで承認保存に続けて本番Neonへ自動反映する。
- Neonの画像URL更新は、管理画面の採用・反映再試行、または承認済みバッチへの明示的な`publish --apply`で行う。画面を開くだけでは反映しない。
- クレジット必須画像は、表示対応完了が明示されるまで反映しない。
- 既存画像・本文を上書きしない。R2の確認用画像を自動削除しない。旧ローカル画像はR2保存とハッシュ検証が済んだものだけ移行時に削除する。
- 公開バケットの確認用プレフィックスを、非公開領域と説明しない。
- 既定5件ずつ。再開・検索し直しは明示的に行い、判断理由・目視確認・権利確認・指示の版・画像ハッシュを残す。
- 適切な写真が無い場合は要確認にする。生成画像は未採用であり、追加を依頼されるまで生成しない。

# 検証

- `.venv/Scripts/python.exe -X utf8 -m unittest discover -s tests -v`でテストする。
- 実データを使う検証は、まず少数を確認用R2へ保存し、`verify`で画像URLが未変更であることを確認する。
- 公開・DBのデータ更新の検証にはモックを使い、実データで確認前の公開を行わない。


## 通常雑学と雑学MAPの切り替え

2026-10-16の指示により、Mapも候補確認・複数枚承認・本番DBへの自動反映に対応する。
既存管理画面の「管理・編集 → 写真の確認 → 写真の管理対象」で「通常の雑学」または「雑学MAP」を選ぶ。
採用ボタンで、選択中の対象へ全写真と写真別出典を同時に反映する。先頭1枚は旧版用のimage_urlにも残す。
通常雑学はpublic.trivia、Mapはpublic.map_triviaへ保存する。管理画面と同じ本番DBを使う。
Mapの確認画像と履歴はR2_REVIEW_PREFIX/map、公開写真はR2_TRIVIA_IMAGE_PREFIX/auto/mapへ分ける。
同じ数値IDでも対象をまたいだ承認・上書きはしない。通常雑学の既存バッチと公開URLは維持する。

CLIは全コマンド共通で、コマンド名より前に --target map を付ける。省略時は従来どおり通常雑学。
例: .\.venv\Scripts\python.exe -m trivia_photo --target map collect --limit 5
例: .\.venv\Scripts\python.exe -m trivia_photo --target map list --batch latest
例: .\.venv\Scripts\python.exe -m trivia_photo --target map review-queue
収集は引き続き手動で、collectだけでは候補を検索しない。collect.mdに従ってsearch・目視・select・verifyまで進める。
Mapの候補が未収集なら確認画面は空になる。対象を指定して写真収集を依頼する。
Mapのimage_credit/image_credit_metadata列を含む毎日雑学側のmigrate_trivia_images移行を先に適用する。
旧ローカル画像のmigrate-localは通常雑学専用。Mapに流用しない。
